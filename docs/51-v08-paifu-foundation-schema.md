## 1. 既存実装の調査

| 境界 | 現状 | 牌譜に必要な補完 |
|---|---|---|
| `Game`構築 | seedと設定で物理牌IDの山をshuffle、8枚×4人を配り、親が最初の1枚を引く | 配牌直後の全手牌・正確な山順・牌ID→種類対応を保存。最初のツモは既に起きている |
| `Game.events.draw` | `{type:'draw',seat}` | ツモ牌IDがない。直後の`drawn`から補完 |
| 打牌・リーチ | `riichi`→`discard`が同じコマンドで発生 | 宣言選択UIは行動ではない。成立した打牌ID・ツモ切り・リーチを順序どおり記録 |
| `respond` | チー・ポン選択は後続判断まで保留。パスはeventsに残らない | 各判断を独立した行動として保存。イベント0件のパス、取り消された鳴きの選択も必要 |
| チー・ポン成立 | seat/from/tile/meldだけ記録 | 消費した手牌2枚と取得牌1枚の実物理IDを補完。選択と成立は区別 |
| 和了 | `win`イベントに和了牌・得点がない | `result`から和了牌・正式解析・基本点Bを保存 |
| 流局 | `exhaustive-draw`あり | 終局状態と移動0点の精算を別々に保存 |
| `finishRound` | `S.scored`で1回だけ`applyRoundResult` | 精算はGameイベント外。局前後の点数・親・連荘・終了理由を別記録 |
| AI経路 | `step`内の`decideCharacter`→`applyAction` | 記録は決定後。判断のために牌譜・他家の秘密をAIへ渡さない |
| 人間/自動パス | `applyHumanAction`→`applyAction` | 手動/AI/自動パスの主体タグを呼出側から渡す。拒否・UIキャンセルを成立行動と偽らない |
| 既存履歴 | `S.history`と`S.match.log`はメモリ内の結果要約 | 行動列・山・初期配牌がなく、完全牌譜ではない |

既存再現URLは`src/ui/replay.js`。seedBase、通し局数、親、親番、連荘、局数、モード、AI/キャラを検証するが、実際に選んだ行動や過去の持ち点は復元しない。実ゲームの山seedは`seedBase + round × 7919`、AI用乱数は別の`createRng(seed ^ 0x5bd1e995)`。牌譜再生はAIを再計算せず、記録した行動をエンジンへ適用する。

既存保存は主に`mj-mode`・`mj-length`・`mj-ai`・`mj-speed`、チー/ポン自動パス、`mj-effects`・音/声設定、初心者進捗`mj-beginner-room-v1`。対戦相手選択は画面メモリ内。これらのキー・内容・例外時の従来動作を変更しない。

## 2. v1スキーマ案

実行定義は`src/engine/paifu.js`。JSONのみ。現時点でUIから未接続で、外部配布用の確定仕様ではない。

```text
format: "mathjong-paifu"
schemaVersion: 1
engineVersion: "0.5.0-a"
ruleVersion: "mathjong-rules-0.5.0-a"
visibility: "private-full"
id: 呼出側が指定する記録ID
createdAt: UTC ISO8601 / null（未計測を捏造しない）
appVersion, sourceRevision: 任意の画面版/完全SHA、未取得ならnull
settings:
  rules: 実際の設定全体（現行数学Ⅰ/Ⅱと内部legacyの完全一致だけ許可）
  players: 席0〜3のkind・内部ID・名前・当時の公開プロフィール
  seedBase: 元URL/試合のseedBase、未取得ならnull
  firstRound: 記録開始の通し局数
  origin: match-start / replay-url / fixture
initialMatch: 記録開始時のMatch状態（途中URLでは全員100点、過去を捏造しない）
status: recording / complete / aborted
rounds[]:
  id: 記録ID + 通し局数
  setup: seed / snapshot（明示したpresetテスト専用）
  atMs: 記録全体の開始からの経過時刻 / null
  matchBefore: 親番・親・連荘・局数・得点などの局前状態
  initial:
    seed / dealer / round / tileType
    wall / hands / melds / rivers
    current / phase / drawn / justDrew / turnCount / claim / riichi / result
    events: 元の最初のdrawイベント
  initialEvents: 最初のツモに牌IDを補ったイベント
  steps[]:
    seq: 1始まりの判断順
    seat, source: human / ai / auto-pass
    action: discard(tile,riichi?) / chi(option) / pon / pass / ron / tsumo
    atMs: 経過時刻 / null
    events[]: この判断で確定したイベント（0件も正常）
      seq: 元Game.eventsに対応する0始まりの順序
      type, engine: 元イベントを変更せず保持
      tile: ツモ/宣言/和了牌の物理ID
      tsumogiri: 打牌時
      tiles: 鳴きで使用した実牌3枚
      result: 和了時の正式結果
    state: 判断後の全物理牌領域・宣言待ち・リーチ・終局状態
           固定メタデータと過去イベント全体は重複保存しない
  settlement: 未精算ならnull
    type: settlement
    seq: 最後のGameイベントの次の番号
    atMs, maxRound
    beforeScores / deltas / afterScores / matchAfter
final: 完走時の得点・同点順位・終了理由・局数・連荘・和了回数・最高獲得点/基本点
termination: 途中退出/リセット/記録エラー時の理由・時刻。それ以外null
```

正しい順序は`rounds`→`steps.seq`→その判断内の`events.seq`。時刻は補助情報であり、未計測のnullを許可する。取得した時刻はnullを挟んでも局間でも逆転を拒否する。`Game.events`に存在しないパスイベントを捏造しない。パスは`steps`の判断として明示する。

物理牌IDは局内で一意。別局の同じ数値IDは別の牌であり、参照キーは局IDとの組。種類ラベルは保存したルール設定と`tileType`から解釈し、数学Ⅱの弧度法は表示側の既存仕様に任せる。

## 3. 実装したAPIと保証範囲

- `captureGame(game)`：固定フィールドを読むだけ。live Game・乱数・AI・DOM・ストレージを変更しない。
- `createPaifu(...)`／`beginRound(...)`：記録開始と、配牌・親の最初のツモ直後を記録。途中局面を開始点と偽らない。既存URLによる途中の「局」開始には対応。
- `appendDecision(...)`：呼出側が通常処理を1回実行した前後を渡す。別のGameで同じ判断を独立に実行し、後状態が一致したときだけ追加。欠落した判断、違う物理ID、間違った主体、不正な行動を検出。
- `settleRound(...)`：既存`applyRoundResult`との完全一致と400点保存を確認。二重精算、精算前の次局、終了後の追加局を拒否。
- `endRecording(...)`：途中退出を流局へ変換せず、未精算の有効な記録として終了。
- `verifyPaifu(...)`：初期配牌・牌保存・全判断・全チェックポイント・生成イベント・精算・最終結果を検証。戻り値は要約のみ。
- `replayPrivateRound(...)`：任意の判断境界を独立Gameへ復元。0は配牌・親の最初のツモ直後。キャッシュのルールを外へ露出しない。
- `encodePaifu`／`decodePaifu`：安定したJSON往復。未知版、未知ルール、破損、危険キー、過度な深さ/ノード数、非有限値、8MiBを超える入力を明示拒否。8MiBは**コードクの処理上限**であり、保存容量の正式決定ではない。

記録は入力から切り離し、深くfreezeする。評価ルールのキャッシュはモジュール自身が作った不変オブジェクトだけで共有。復元Gameの継続・ルール変更によって元の記録やキャッシュが変化しない。標準shuffleとpresetで異なるGame用RNG初期化経路も保つ。

**保証の限界**：検証は合法な行動列・状態の整合性であり、プレイヤーの本人性や改ざん不能性を証明する電子署名ではない。途中で切れた有効なprefixを元試合の全履歴と断定しない。`source`は呼出側が渡す由来情報で、保存していない自動パス設定ON/OFFを証明しない。手牌のUI表示順、スクロール、ヒント閲覧、宣言選択キャンセルなどのUI操作履歴は今回の対象外。

## 4. 通常対局への接続は未実施

このモジュールは`app.js`・AI・Gameからimportされていない。通常対局が自動記録・自動保存する機能は**まだない**。既存コードをmonkey patchしない。将来はGame構築後、既存の行動適用の直前/直後、精算ガード内、次局・タイトル退出に小さな接続を設ける。

記録処理が失敗しても既に成立したゲーム操作を巻き戻してはいけない。接続時には例外を分離し、有効prefixを`recording-error`で閉じて、ゲーム進行を維持する設計・テストが必要。現在は接続していないため通常対局に新しい例外経路を追加していない。

Game用RNGは復元するが、**任意時点から将来のAI判断を同じ乱数位置・キャラ内部メモリで再開する機能は未実装**。現段階の再生は保存した判断を実行する。AIやルールが更新された将来版は、版ごとの互換実装/移行を設計し、古いデータを黙って新しい意味に読み替えない。

## 5. 重大な設計事項：候補比較とディレクターへの提案

### 保存媒体（未採用）

| 候補 | 利点 | 問題 |
|---|---|---|
| localStorageの別キー | 導入が容易 | 同期処理、端末の小さい容量上限、複数牌譜の一括書換え。既存キーとの容量競合 |
| IndexedDBの独立DB | 非同期、局/試合を分割、原子的な更新 | Safariの容量・消去・プライベートブラウズ、移行/復旧の実測が必要 |
| 手動JSON出力/入力のみ | 保存容量をユーザーが管理、導入が小さい | リロード前の未出力損失、公開・共有範囲の説明が必要 |

**推奨候補は独立IndexedDB**。ただし今回はDB名・ストア・新キーも実際には作らず、既存キーの変更・自動削除はしない。容量・保持件数・ユーザー削除・破損復旧・保存失敗通知・移行を別途決める。長い連荘に備えた分割保存/サイズ上限時の扱いも未決定。

### データ量と復元方式

| 方式 | 利点 | 問題 |
|---|---|---|
| eventsだけ | 小さい | 現行eventsではパス・保留・ツモID不足 |
| 初期状態＋判断だけ | 小さい | 将来のルール差・記録漏れが検出しにくい |
| 初期状態＋判断＋状態チェックポイント | 誤記録を検出し、任意の判断後を厳密照合 | 大きくなる |

今回は内部基盤として3番目を実装。圧縮や間引きは正確性・サイズ実測後に検討し、復元検査を弱めて容量を削らない。詳細なサイズ・時間は検証記録へ追記する。

### 非公開情報と共有

完全牌譜は他家の手牌・山順を含むため、**そのままAIの入力や対局中の表示・公開共有に使ってはいけない**。`private-full`は分類であって暗号化やアクセス制御ではない。今回、公開用projection・共有URL・アップロード・振り返り画面は作らない。終了後にどこまで表示/共有するかは別途承認が必要。将来の画面でも名前等をHTMLへ無加工挿入しない。
