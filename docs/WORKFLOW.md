## 3. 開発1サイクル

1. **着手前**：GitHub実態確認→既存仕様との差分・安全条件を整理→包括承認内は自律開始し、対象外の重大変更は相談する。
2. **実装**：最新mainから `feature/` または `fix/` ブランチ。コード+テスト+版別の実装記録を一緒に残す。専用プレビューサイトはオーナーが希望していないので原則設置しない。
3. **報告/PR**：目的、差分、影響、テストコマンド・結果、失敗や未実行、既知リスク、固定HEADをMarkdownで共有。Draft PRを作り、対象SHAを固定する。
4. **独立監査**：Codexがhead/base、差分、関係コード、情報漏えい、数学的正確性、UI、再現URL、性能、統計、テスト妥当性を独立検証。**P0/P1/P2/P3に分類**し、行・手順・影響・対策を報告。結果はどのSHAに対するものか明記。
5. **修正時**：Claudeが直し、**HEADが変われば再監査**。監査対象とマージ対象を一致させる。P0/P1/P2は原則解消を必要とし、P3の残す/直すはオーナーに判断してもらう。
6. **マージ**：包括承認または個別承認の範囲と安全条件確認→HEADとmain再取得→必要ならDraft解除→チェック・保護再確認→**expected_head_shaを付けて**正式マージ→実main SHA・merged確認。条件を迂回しない。
7. **公開と正式受入**：既存GitHub PagesでiPhone Safari実機テスト。ユーザーのチェック項目、結果、未確認事項を記録。mainマージと正式完成は別イベント。
8. **引き継ぎを更新**：main SHA、PR、未解決事項、判定、次担当の作業を更新し、チャットの長さに依存しない状態で次へ。

## 4. 文書を更新するタイミングと責任

少なくとも**新しいPR/重要な監査結果/mainマージ/実機結果/仕様決定/開発順序の変更**時に、以下を確認する。

| ファイル | 更新するもの |
|---|---|
| `docs/HANDOFF.md` | 最新の版、main SHA/PR HEAD・状態、公開検証、次の1手、未解決P0〜P3 |
| `docs/DECISIONS.md` | 日付、オーナー決裁、決定と保留、旧決定からの変更経緯 |
| `docs/ROADMAP.md` | 完了/PR中/実機待ち/提案中を別々に更新 |
| `docs/WORKFLOW.md` | 役割や監査・公開運用が正式に変わった場合のみ更新 |
| `docs/CHAT_START.md` | 新チャットが1回で読み始められる入口、参照先の変更 |
| `docs/19-ver0.4-b-independent-audit-acceptance.md` など | 各版の証拠。監査の数値/限界、テスト/実機報告の出所を保存 |
| `README.md`, `AGENTS.md` | 新規担当が最初に見たときに古い指示を現行と誤認しないか確認 |

更新担当は作業を指揮するディレクター。Claudeに文書更新を依頼しても、**ChatGPT/オーナーが最終的に状況との整合をチェック**する。既存資料は履歴として保存し、先頭の「旧版」注記や新資料へのリンクで誤認を防ぐ。無言の削除・歴史改変をしない。

原則、**文書専用ブランチ→Draft PR→整合性・安全条件確認→包括承認内なら自律マージ、対象外なら個別承認→main**。ゲーム本体や役点の説明は現状と提案を区別し、未承認の新仕様を事実にしない。

## 5. 検証と統計の最低限の保存

- `npm test`、`node tests/e2e/play.mjs`、`tools/simulate*.mjs` は**実行できたものだけ**結果を記す。標準コマンドは実装記録/各ツールのヘルプを確認。ブラウザ付属バイナリがない場合、代替ブラウザ名と版を記録。
- **再現**：コードSHA、base/head、数学Ⅰ/Ⅱ、局数、難易度、seed、実行条件、Node/ブラウザ、実測日時、試合数と組数を残す。集計JSONが生データではない場合は**「集計結果」**と明示。
- **統計**：席替え試合の標準誤差は**独立の組単位**。生の組別データを別途残せれば、他のAIが集計値を再計算できる。AUCは同点0.5補正が必要（P3-2修正待ち）。
- サンプルサイズが小さい、探索的に追加検定をした、iPhone実測でない、学習データ上のみの値等の限界を必ず書く。
- 公開情報限定AIの保証は**実行経路**で確認し、学習ラベル生成の非公開手牌使用と混同しない。

## 6. 別チャットへの完全引き継ぎ手順

1. 新しいチャットに[CHAT_START](CHAT_START.md)の「コピー用プロンプト」を貼る。**説明文や旧チャットの全文は不要**。
2. 新担当はGitHubのmain SHAとPR状態を照会し、五つの標準資料と`docs/18`の歴史的文書、必要なコード/最新実装記録を読む。
3. 新担当は**現行版、正式承認、未マージPR、P3、具体的な次の作業、根拠URL/SHA、不確実性**を報告してから提案。
4. 新担当が本書と異なる情報を見つけたら「GitHubの事実を優先し、どの項目が古かったか」を指摘。いきなりソースを書き換えない。
5. ディレクター/オーナーが復元テストを評価。不足資料はdocsのDraft PRで修正し、承認されたらmainへ反映。以後すべての節目に上の更新ルールを適用。
