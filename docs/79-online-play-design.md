## 1. 前提と範囲

- 部屋コードで入る友達対戦。人間2〜4人、空き席は既存のキャラクターAI（12人）で埋めて4人打ちにする。2人以上でホストが開始できる。
- 長さは1局戦・4局戦・8局戦のすべて（決定済み）。
- 土台は Firebase プロジェクト `asumath-games` の Realtime Database（asia-southeast1）。置き場所は `games/mathjong/rooms/<code>`。
  - 接続情報は FACTOR×FACTOR の `FB_CONFIG` と同じ（いろヨミも同じ値を転記して使用）。
  - SDK はいろヨミと同じ `firebasejs/12.12.0` を、**オンラインに入るときだけ動的に読み込む**（オフラインの対局・初心者の部屋に影響させない。牌譜の機能を動的 import にしたのと同じ考え方）。
- **Spark プランを前提とする**（FACTOR 側の方針：Blaze 化・Cloud Functions を使わない）。そのため、サーバー側で手牌を隠して判定する仕組み（サーバー権威）は作れない。

## 2. 監査：現行のエンジン・試合管理・画面のオンライン化適性

### 2.1 エンジン（`src/engine/game.js` の `Game`）

| 観点 | 現状 | オンライン化での評価 |
|---|---|---|
| 決定論 | `new Game({ rules, seed, dealer, players, round, ruleset })` で山・配牌が決まる。乱数は `createRng(seed)`（mulberry32）。エンジン内に時刻・`Math.random` の利用なし | ◎ ホストでの実行、記録からの再生（牌譜の `replayPaifuRound`・`stateDigest` と同じ仕組み）に向く |
| 判断待ち | `pending()` が「誰の何の判断か」を1件だけ返す（`turn` か `claim`） | ○ ホストの進行ループの起点としてそのまま使える |
| 公開情報 | `viewFor(seat)`：自分の手牌＋全員の公開情報。AIにもこれだけを渡す方針 | ◎ ゲストへの配信内容の基準にできる |
| 宣言ウィンドウ | `_openClaims` で宣言できる席の列（打牌者から近い順）を作り、`respond()` で**1席ずつ順番に**判断する。ポン・チーは保留し、後続の席のロン判断が終わってから確定する。より近い席のポンが保留中なら、後続の席の選択肢からポン・チーが消える（`_claimOptions`）。ロンが出たらその場で和了（アタマハネ） | △ 1席ずつ問う作りなので、人間が複数いると最大で「人数×制限時間」待つことになる。**並列で集めて、順番どおりに適用する層**が必要（4章） |
| 不足点 | ① 宣言の「締切」「時間切れ＝パス」の概念がない<br>② 手番の打牌に時間制限がない<br>③ 状態の保存・復元の API がない（デッドウォールなどが閉包の中） | ① ②はホストの進行ループに追加する（エンジンは変えない）<br>③は**行動の記録と再生で代替する**（牌譜と同じ方式。5.4・8.3） |
| ID の秘密性 | 牌の id → 種類の対応はルールから決まる固定の表（`tileType`）。山の**並び**だけが秘密 | ○ 打牌の id を公開しても秘密は漏れない |

### 2.2 試合管理（`src/engine/match.js`）

- `createMatch`・`applyRoundResult`・`dealerOf`・`handLabel`・`ranks` はどれも純関数で、状態は普通の JSON。**そのまま配信できる**。
  - 親・連荘・持ち点・供託・アガリやめ・試合終了の判定を含む。
- 局をまたぐ進行（次局の `seed = seedBase + round × 7919`、`MAX_ROUND` での打ち切り、精算、最終結果）は **`app.js` の `finishRound`・`startRound`・`next` の操作の中にある**。そのためホスト側に「試合の進行役」を切り出す必要がある。
- 不足点：
  1. 「全員が結果画面を見て次局へ進む」合意の仕組みがない（ローカルでは本人が「次の局へ」を押すだけ）。
  2. 最終結果・再戦（`again`）が画面の操作に直結している。
  3. 精算結果はホストが計算して配信すればよく、ゲスト側の再計算は不要（表示用の `prevScores`・`lastRound` も配信する）。

### 2.3 AI と乱数

| 項目 | 現状 | 評価 |
|---|---|---|
| AI の乱数 | `startRound` で `S.aiRng = createRng(seed ^ 0x5bd1e995)`。局ごとに seed から作り直す | ◎ ホスト集約と相性がよい（ホストだけが持てばよい） |
| AI への入力 | `decideCharacter(g, seat, id, S.aiRng, { ...matchInfo(S.match), publicHistory }, seatIds)`。追加3人は `publicGame(game, seat)` の公開版を使う | ◎ すべてホストにある情報 |
| 局をまたぐ AI の状態 | `S.publicAiHistory`（`recordPublicRound` で公開イベントから作る）・`S.aiDecisionsBySeat`（集計用） | ○ ホストだけが持つ。ホストの再読み込みからの復帰では、試合の行動記録から作り直す |
| 時刻への依存 | AI の判断に時刻・`Math.random` の利用なし（`performance.now` は計測用のローカル表示だけ） | ◎ |
| `Math.random` の利用 | `seedBase` の決定・相手の抽選・座席の割り当て（`app.js`） | ○ ホストだけが行う。**`seedBase` はゲストに渡さない**（渡すと全員の配牌・山が再現できる） |
| 乱数の状態の保存 | `createRng` の内部状態は閉包の中で取り出せない | △ ホストの復帰時は、局の行動記録を再生しながら AI の判断をもう一度呼んで乱数を同じだけ進め、記録と一致することを確かめる（8.3） |

### 2.4 進行ループ（`app.js`）のうち、ネットワークの境目に載せ替える部分

| 現在の仕組み | オンラインでの扱い |
|---|---|
| `step()`：`pending()` を見て、AI の番なら `setTimeout`（`speedDelays`：通常 700/350ms）の後に `decideCharacter` → `applyAction` → `step()` | **ホストの進行ループ（HostRunner）に移す**。人間の席の番では「行動の到着」か「時間切れ」を待つ |
| `applyHumanAction` / `humanAct`：手元の `Game` に直接適用 | ゲストは `act/$seat` に書くだけ。ホストが検証して適用する（エンジンが拒否したら無視し、その旨を返す） |
| チー・ポンの自動パス（`autoPassDue`）・リーチ後の自動ツモ切り（`scheduleAutoTsumogiri`） | **各端末の設定のまま、端末側で自動的に行動を送る**（ホストに設定を預けない）。時間切れの扱いとは別 |
| `finishRound`（精算・`publicAiHistory`・牌譜・卒業試験）、結果画面の「次の局へ」（`next`） | ホストが精算して配信する。「次へ」は全員の準備完了か20秒で締める |
| 演出・効果音（`fxScan`・`soundScan` が `g.events` の増分を見る）、演出の待ち行列 | 端末ごとに表示するだけで、ゲームの進行は待たせない（現行の方針どおり）。配信する公開イベントの列から同じ増分を作る |
| 手牌の長押し並べ替え中は `step()` を後回し（`S.stepDeferred`） | ゲスト側は表示順だけの話なので、ホストの進行とは無関係になる |
| `HUMAN = 0` の前提（`app.js` 73か所）と `S.game` の直接参照（65か所） | **自分が席0になるよう回転した表示用モデル（RemoteTable）**を各端末で作れば、描画の大半を変えずに使える（7.2） |
| 牌譜（`paifu.*`） | オンラインでは記録しない（対象外の理由 `'online'`）。たたき台どおり |

### 2.5 情報の境目（何をゲストに渡してよいか）

- **公開**：
  - 河（ツモ切り・リーチ宣言牌を含む）、公開面子、各席の手牌の**枚数**
  - 親、リーチ宣言、ドラ表示牌、残り枚数、通常ツモの回数
  - 持ち点・供託、公開の出来事（打牌・鳴き・暗カン・和了・流局）
  - 局の結果（和了者の手・役・点数）と精算
- **本人だけ**：
  - 自分の手牌・ツモ牌
  - 自分の判断の選択肢（ツモ和了可・リーチ候補・暗カン候補・ロン/ポン/チー候補）
  - 自分のフリテンの理由・リーチの待ち・`ronBlocked`
- **誰にも渡さない**：
  - 山の並び・王牌の未公開の牌
  - `seedBase` と局の seed
  - 他家の判断の候補・他家の見送り・AI の内部状態
- 牌譜の振り返り（docs/77）と同じ境目で、すでに `paifu-review.js` で「`viewFor` と同じ範囲だけを射影する」実装と検証の実績がある。これを流用できる。

## 3. 同期方式の比較と推奨

| 観点 | (A) ホスト権威型（推奨） | (B) 全端末決定論ロックステップ |
|---|---|---|
| 仕組み | ホストだけが `Game`・試合管理・CPU を動かし、公開状態と席ごとの手牌を配信する。ゲストは自分の行動だけ送る | 全端末が同じ seed で `Game` を動かし、行動イベントだけを交換する |
| 工数 | 中〜大。<br>・ホストの進行ループ<br>・配信の射影<br>・ゲストの表示用モデル<br>・行動の検証 | 一見小さい（イベントを交換するだけ）が、次のものが別に要る：<br>・時間切れの合意（誰が「時間切れ」と決めるか＝結局ホストが要る）<br>・全端末の AI のコードの版の一致<br>・ずれの検出と復旧 |
| チート耐性 | ゲストは他家の手牌・山を**読めない**（ルールで拒否）。ホストは見られる | **全員が全手牌・山を持つ**。開発者ツールで丸見え。手牌を隠す設計そのものが成り立たない |
| 破綻条件 | ① ホストのタブが止まる（iPhone で裏に回る・画面ロック）と全員が止まる<br>② ホストの回線断<br>③ 書込みの遅延が大きい | ① 版の違い・浮動小数の違い・取りこぼしたイベントでの**状態のずれ**（静かに壊れる）<br>② 時間切れの判定のずれ |
| 切断時 | ゲストの切断：ホストが CPU で代打ちし、復帰したら席に戻す（容易）。<br>ホストの切断：猶予の間は一時停止し、ホストの再読み込みで復帰。猶予を過ぎたら途中終了（8.3） | ゲストの切断：残りの端末が代打ちを決定論で行う必要がある（全員の合意が要る）。<br>ホストの切断：判定役の引き継ぎが要る |
| 既存資産 | エンジン・AI・試合管理・射影（docs/77）をそのまま使える | エンジン・AI は使えるが、`stateDigest` によるずれの検出の仕組みを新たに作る必要がある |

**推奨：(A) ホスト権威型。** 手牌を隠せること、エンジンを変えずに済むこと、切断の扱いが単純なことが決め手です。(B) は時間切れの判定のために結局ホストが要るうえ、手牌を隠せず、静かに状態がずれる危険があります。

(A) の破綻条件と対策：

| 破綻条件 | 対策 |
|---|---|
| ホストのタブが裏に回る・画面ロック（iPhone Safari はタイマーを止める） | ホストの画面に「このタブを開いたままにしてください」を常時表示する。ゲスト側はホストの生存（`presence`）が10秒途絶えたら「ホストの接続を待っています」と出して一時停止。ホストが戻れば続きから（8.3） |
| ホストが猶予（推奨90秒）を過ぎても戻らない | 試合を途中終了し、それまでの持ち点・順位を表示する（引き継ぎはしない：未決事項） |
| 書込みの遅延 | シンガポールのリージョンで日本からの往復はおおむね100ms前後の見込み（未計測）。CPU の行動は従来どおり700ms間隔なので体感への影響は小さい見込み |

## 4. 宣言ウィンドウ・手番の時間

### 4.1 宣言ウィンドウ（ロン＞ポン＞チー）を複数端末へ広げる

エンジンは「宣言できる席の列」を近い順に1席ずつ問う。オンラインでは次の2段にする。

1. **窓を開く**：打牌で `phase === 'claim'` になったら、ホストは `claim.queue` の中の**人間の席**について、その時点の選択肢（ロン・ポン・チー候補）を各席の `priv` に書く。全員に**同時に**出し、締切（15秒後）も書く。
   - CPU の席はまだ判断させない。
2. **締める・適用する**：対象の人間全員の応答が揃うか、締切で締める。時間切れの席はパス。
   - ホストはエンジンの順番どおりに `pending()` を回す。CPU の席はその時点で `decideCharacter`、人間の席は集めた応答で `respond()` する。
   - 集めた応答がその時点では成立しない場合（例：より近い席のポンが保留中で自分のポンが消えている）は、**パスに直して**適用する（エンジンの例外を起こさない）。
   - ロンの選択肢は他の席の選択で消えないので、ロンは必ず有効。

この方式の結果は、ローカルの1席ずつの判断と**同じ**になる。

| 場面 | 結果 |
|---|---|
| アタマハネ | 近い順の最初のロンで和了。後ろの応答は捨てる |
| ロン＞ポン | ロンが出れば保留中のポンは成立しない |
| 後続ロンによるチーの取消し | チーは保留のまま、後続のロンで流れる |
| ポン＞チー | 近いポンが優先される |

エンジンは変えずに、ホスト側の「応答を集めて順に流す」層だけで実現できる。

ローカルとの違いと影響：

- ローカルでは、より近い席（CPU）のポン保留を知った後で人間に選択肢が出る（ポン・チーが消えて、ロンだけが出る）。並列方式では、人間は**最初の選択肢**を見て選ぶ。
- 選んだポン・チーが通らないことがあり、その場合は「他家の宣言が優先されました」と表示する。
- 情報の漏れはむしろ減る（他家の保留を推測できない）。

時間による情報の漏れ：

- 人間に宣言の選択肢があると、他の全員は最大15秒待たされる。そのため「誰かが鳴ける」ことが分かる（ローカルでも AI の判断の間にある程度は同じ。対面の麻雀の「考える間」と同じ性質）。
- 隠す方法として、打牌のたびに一定の待ちを入れる案はあるが、テンポが大きく落ちる。**v1 では隠さない**（未決事項 U5）。

### 4.2 制限時間（推奨値）

| 判断 | 推奨 | 時間切れの扱い | 理由 |
|---|---|---|---|
| 宣言（ロン・ポン・チー） | **15秒**（たたき台どおり） | パス（ロンができてもパス） | 3枚の数式面子を見て判断する必要があるので、10秒では短い。20秒を超えると、宣言のたびに全員を待たせる時間が長すぎる |
| 自分の手番（打牌・ツモ和了・リーチ・暗カン） | **45秒**（たたき台になし・追加を提案） | ツモ切り（ツモ和了・リーチ・暗カンはしない） | 数学的な判断で考える時間が要る。無制限だと1人の離席で全員が止まる |
| リーチ中の手番 | 待たない | 端末の自動ツモ切りが ON ならすぐに。OFF なら手番の時間の対象 | 現行の自動ツモ切りの機能をそのまま使う |
| 局の結果画面から次局へ | **20秒** | 全員の「次へ」か20秒で次局へ | 結果を読む時間を確保する |
| 連続の時間切れ | 3回続いたら | その席を「離席中」として CPU の代打ちに切り替え。本人の操作で戻れる | 放置の人で全員が待たされないように |

- 時間は**ホストの時計で判定**する。締切の時刻は `serverTimeOffset` で補正した時刻で配信し、ゲストの表示用にだけ使う。
- 端末ごとの時計のずれで判定が変わらないよう、締切を判定するのはホストだけ。

## 5. 非公開情報（手牌）の配信とルール

### 5.1 方式：席ごとに分けて、本人の uid だけが読める

- Realtime Database のルールは、**親で読取を許すと子では取り消せない**。そのため `rooms/$code` には読取の権限を付けず、子ごとに付ける。
- `priv/$seat` は「`seats/$seat/uid === auth.uid`」の人だけが読める。書けるのはホストだけ。
- 公開状態（`pub`）は部屋の参加者だけが読める。書けるのはホストだけ。
- 行動（`act/$seat`）は本人だけが追記でき、読めるのはホストと本人。
- ホストの秘密（`host`：`seedBase`・行動の記録・AI の判断の記録）はホストだけが読み書きできる。

### 5.2 割り切りとリスク

- **ホストは全員の手牌を知り得る**（ホストが `Game` を動かすため）。
  - サーバーがない Spark 版では避けられない。友達対戦の範囲で受け入れる案とする。画面に「ホストの端末で対局を進めます」と明記する。
  - 防ぐには Cloud Functions（Blaze）でサーバー権威にする必要がある（未決事項 U1）。
- ゲストは改ざんした行動を送れるが、ホストのエンジンが検証して拒否する（不正な打牌・不正な鳴きは成立しない）。他席の行動はルールで書けない。
- いろヨミのルール（`rooms/$code` に認証済みなら誰でも読み書き可）は**数雀には使えない**（手牌が全員に見えてしまう）。数雀は別の枝 `games/mathjong` を追加する。

### 5.3 ルール断片案（`games/mathjong`）

いろヨミと同じ作法で進める。

- FACTOR 側の `scripts/prepare-iroyomi-rules.cjs` に倣い、`prepare-mathjong-rules.cjs` を作る。
- 現行のルール全文（Console から書き出したもの）を入力にする。
- 「`games/mathjong` が存在しないこと」「祖先に広い権限がないこと」を確かめる。
- 追加した枝以外が完全一致することを `deepEqual` で検査する。
- 候補を出力するだけで、本番には接続しない。適用は所有者が Console で行う。

```js
// firebase/mathjong-rules.cjs（案）：games/mathjong の中身だけ。既存の枝には触れない
const R = (code) => `root.child('games/mathjong/rooms/' + ${code})`;
const room = R('$code');
const isHost = `${room}.child('meta/hostUid').val() === auth.uid`;
const seatUid = (s) => `${room}.child('seats/' + ${s} + '/uid').val()`;
const isMember = `(${[0, 1, 2, 3].map((s) => `${seatUid(`'${s}'`)} === auth.uid`).join(' || ')})`;
const notExpired = `${room}.child('meta/expiresAt').val() > now`;

module.exports = {
  // 機能の停止スイッチ（Console からだけ書く）。クライアントは読むだけ
  config: { '.read': 'auth != null', '.write': false },
  rooms: {
    // 一覧は読ませない。期限切れの部屋は、認証済みなら誰でも「丸ごと削除」だけできる（サーバーなしの掃除）
    $code: {
      '.write': `auth != null && data.exists() && data.child('meta/expiresAt').val() < now && !newData.exists()`,
      '.validate': `$code.matches(/^[A-HJ-NP-Z2-9]{6}$/)`,
      meta: {
        // 部屋の存在と設定は、コードを知っていれば読める（参加の前に必要）
        '.read': 'auth != null',
        // 作成は「無い部屋を自分をホストにして作る」だけ。以後の変更はホストだけ
        '.write': `auth != null && ((!data.exists() && newData.child('hostUid').val() === auth.uid) || (data.exists() && ${isHost}))`,
        '.validate': `newData.hasChildren(['hostUid','status','mode','length','ruleset','appVersion','createdAt','expiresAt'])
          && (newData.child('length').val() === 1 || newData.child('length').val() === 4 || newData.child('length').val() === 8)
          && newData.child('ruleset').val() === 2
          && newData.child('mode').val().matches(/^math[12]$/)
          && newData.child('expiresAt').val() <= now + 12*60*60*1000`,
      },
      seats: {
        '.read': 'auth != null',
        $seat: {
          // 空席を自分の uid で取る（ロビー中だけ）／自分の席の更新・離席／ホストはすべて
          '.write': `auth != null && $seat.matches(/^[0-3]$/) && ${notExpired} && (
              ${isHost}
              || (!data.exists() && newData.child('uid').val() === auth.uid && ${room}.child('meta/status').val() === 'lobby')
              || (data.child('uid').val() === auth.uid && (!newData.exists() || newData.child('uid').val() === auth.uid)))`,
          '.validate': `!newData.exists() || (newData.child('name').isString() && newData.child('name').val().length >= 1 && newData.child('name').val().length <= 10)`,
        },
      },
      // 接続の有無（onDisconnect で false）。本人だけ書く
      presence: { '.read': 'auth != null', $uid: { '.write': `auth != null && auth.uid === $uid` } },
      // 公開状態（スナップショット）と公開イベントの列：参加者だけが読み、ホストだけが書く
      pub: { '.read': isMember, '.write': isHost },
      // 席ごとの非公開（手牌・自分の選択肢・締切）：その席の本人だけが読む
      priv: { $seat: { '.read': `${seatUid('$seat')} === auth.uid`, '.write': isHost } },
      // 行動：本人が追記するだけ（上書き・削除は不可）。ホストと本人が読む
      act: {
        $seat: {
          '.read': `${isHost} || ${seatUid('$seat')} === auth.uid`,
          $n: {
            '.write': `!data.exists() && ${seatUid('$seat')} === auth.uid`,
            '.validate': `newData.hasChildren(['k','sid','at']) && newData.child('k').val().matches(/^(discard|tsumo|ankan|ron|pon|chi|pass|ready|away|back)$/)`,
          },
        },
      },
      // ホストの秘密（seedBase・行動の記録・AI の判断の記録）：ホストだけ
      host: { '.read': isHost, '.write': isHost },
    },
  },
};
```

- 上は**断片の案**であり、実装の段階1でエミュレータ上のルール試験（読めてはいけない組合せをすべて試す）とともに確定させる。
- `isMember` を4席の比較で書いているのは、ルールで配列の検索ができないため。
- `ruleset` を 2 に固定しているのは、未決事項 U6 の推奨（現行の版に固定）に合わせた案。

## 6. RTDB スキーマ案（`games/mathjong/rooms/<code>`）

| ノード | 中身 | 書く人 | 読む人 |
|---|---|---|---|
| `meta` | `hostUid`, `status`（`lobby`/`playing`/`result`/`final`/`paused`/`closed`）, `mode`（`math1`/`math2`）, `length`（1/4/8）, `ruleset`（2）, `appVersion`, `createdAt`, `expiresAt`, `startedAt`, `matchNo`（再戦ごとに+1） | 作成時は作成者。以後はホスト | 認証済み |
| `seats/<0-3>` | `{ uid, name, kind: 'human'｜'cpu', cpuId, away: bool }` | 空席は本人が取る。以後は本人かホスト | 認証済み |
| `presence/<uid>` | `{ online: bool, at }`（`onDisconnect().set({online:false})`） | 本人 | 認証済み |
| `pub/state` | 公開状態のスナップショット：<br>`seq`, `round`, `dealer`, `match`（`match.js` の JSON）, `rivers`, `melds`, `handCounts`, `riichi`, `dora`, `wallCount`, `normalDraws`, `turn`（誰の番か・締切）, `claimOpen`（宣言を受付中か・締切。誰に選択肢があるかは出さない）, `result`（局の結果・精算）, `final` | ホスト | 参加者 |
| `pub/ev/<n>` | 公開イベントの列（演出・効果音・最後の打牌の表示用。牌譜の振り返りと同じ射影） | ホスト | 参加者 |
| `priv/<seat>` | `{ seq, hand: [id…], drawn, options: {canTsumo, riichi:[…], ankan:[…], claim:{ron,pon,chi:[…]}}, furiten, waits, deadline }` | ホスト | その席の本人 |
| `act/<seat>/<n>` | `{ k, tile, option, tileType, riichi, sid, at }`（`sid`＝応答している `pub/state.seq`。古い局面への応答を捨てるため） | 本人（追記のみ） | ホスト・本人 |
| `host` | `{ seedBase, round, log: [各局の行動の列], aiLog }`（ホストの復帰用） | ホスト | ホスト |

- 配信の方式：行動のたびに、ホストが**1回のまとめ書き**（`update`。複数の場所を同時に書く）で `pub/state`、新しい `pub/ev/*`、変わった `priv/*` を更新する。ゲストはスナップショットを描くだけなので、再接続しても最新の `seq` から描き直せる。
- 容量の見積もり（概算）：
  - 1回の書込み：`pub/state` 2〜4KB、`priv` 0.5KB
  - 8局戦：約1000回の書込みで、書込み約3MB、ゲスト3人の受信合計で約10MB
  - Spark の受信 10GB/月なら、8局戦を数百〜千試合ほど回せる（他ゲームとの共有分を除く）

## 7. 画面遷移・表示

### 7.1 画面遷移案

```
タイトル ─「オンライン対戦」→ オンライン入口
  ├ ニックネーム入力（初回1回。端末に保存。1〜10文字）
  ├「部屋を作る」→ 設定（数学Ⅰ/Ⅱ・1/4/8局戦）→ ロビー（ホスト）
  └「部屋に入る」→ 6文字のコード → ロビー（ゲスト）
ロビー：4席の一覧（人間の名前／空席は CPU 予定）・設定（ホストだけ変更）・部屋コードの共有・退出
  └ ホストが「開始」（人間2人以上で押せる）→ 対局
対局：既存の卓画面（自分が下・席を回転）＋締切の残り時間＋接続状態の表示
  └ 局の結果（全員の「次へ」か20秒）→ 次局 … → 最終結果
最終結果：「再戦（同じ部屋・同じメンバー・同じ長さとモード）」（ホスト）／「部屋を出る」
  └ 再戦：全員の「準備OK」で開始（抜けた人の席は CPU に。人間が2人未満ならロビーへ戻る）
```

### 7.2 席の回転と表示用モデル（RemoteTable）

- ホストは配信値を**絶対の席番号**で書く。各端末は自分の席を0にして読み替える（`local = (global − mySeat + 4) % 4`）。親・持ち点・河・面子・イベントの `seat`・`from` も同じように読み替える。
- これにより、`HUMAN = 0` を前提とした既存の描画（卓の配置・名札・自分の手牌・宣言の表示・演出の席）をそのまま使える。
- 各端末は、配信値から `Game` と同じ読み取り口（`pending()`、`hands[0]`、`rivers`、`melds`、`riichi`、`events`、`typeOf`、`viewFor(0)`、`riichiOptions(0)`、`furitenOf(0)`、`isClosed` など、画面が実際に使う部分だけ）を持つ表示用モデル `RemoteTable` を作り、`S.game` の代わりに渡す。
- ヒント・選んだ牌の聴牌プレビュー・待ちの表示は `viewFor(0)` と自分の情報だけで動く既存の仕組みのため、変更は小さい。
- ホストの端末も、自分の席を `RemoteTable` で描く（ホストの画面だけ別の作りにしない。ホストの端末で手牌が見えてしまう経路を減らすため）。

## 8. 切断・復帰

### 8.1 検知

- `presence/<uid>` を `onDisconnect` で `online:false` にする。
- ホストは、ゲストが10秒続けて `online:false` なら、その席を「離席中」にする。

### 8.2 ゲストの切断・復帰

- **離席中の席は CPU が代打ち**する。
  - 代打ちの AI は中級の既定キャラクター（未決事項 U7）。
  - 代打ちが始まるのは、その席の判断の番か、宣言の窓が締まるときから。
- 同じ端末・同じブラウザ（匿名認証の uid は保存される）で部屋に入り直すと、`seats` の uid が一致するので**自分の席に戻れる**。
  - 戻るのは、次の自分の判断の番から（宣言の途中では戻らない）。
  - 戻ったら `priv` の最新から描き直す。
- 別の端末・プライベートモードでは uid が変わるため、戻れない（未決事項 U8）。

### 8.3 ホストの切断・復帰（方式Aの扱い）

- ホストの `presence` が途絶えたら、ゲストは「ホストを待っています」と表示する。進行はホストにしかできないので、自然に止まる。
- **ホストの復帰**：ホストが同じ端末で入り直すと、`host`（秘密）から次のものを読む。
  - `seedBase`
  - 現在の局の行動の記録
  - AI の判断の記録
- そこから局を**再生**する。
  - 人間の行動はそのまま適用する。
  - AI の手は `decideCharacter` をもう一度呼んで、同じ乱数を消費しつつ記録と一致することを確かめる。
  - 局の初めからの `stateDigest` を照合する（牌譜の検証と同じ仕組み）。
  - 試合の状態（`match`）と `publicAiHistory` は、公開状態と記録から作り直す。
- **猶予は90秒**（推奨）。過ぎたらゲストの画面で「ホストが戻らなかったため終了」とし、最後に精算済みの局までの持ち点・順位を表示して終える。
- **ホストの引き継ぎ（別の人がホストになる）は v1 ではしない**。
  - 引き継ぐには `seedBase` と行動の記録を新しいホストに渡す必要がある。
  - ルールでは「ホストが本当に落ちたか」を確かめられないため、ゲストが意図的にホストを奪って手牌を見る抜け道ができる（未決事項 U3）。

### 8.4 その他

| 場面 | 扱い |
|---|---|
| 版の違い | 入室時に `meta.appVersion` と自分の版を比べ、違えば「ページを再読み込みしてください」と出して入れない |
| 部屋の期限 | 作成から12時間（`expiresAt`）。ホストは終了時に部屋を削除する。期限切れの部屋は、誰でも丸ごと削除だけできる（サーバーがないための掃除） |

## 9. 実装の段階分割

各段階は「通しで遊べる」単位で切る。実装は全長さ対応を前提とし、通しの確認順として1局戦を先に使う。各段階は別PRとし、Codex の監査とオーナーの受入を経てからマージする。

### 9.0 共通のテスト基盤（段階1で用意）

| 層 | 方法 |
|---|---|
| ① 単体（Node・ネットワークなし） | `Transport` を抽象化し、メモリ上の偽バスでホスト1＋ゲスト3を同じプロセスで動かす。次を偽の時計で決定論的に試す：<br>・宣言の並列収集とエンジン順の適用<br>・時間切れ<br>・代打ち<br>・ホストの再生による復帰<br>4・8局戦の通しも数秒で回せる |
| ② ルール試験 | FACTOR と同じく `firebase-tools@14.27.0`＋Java 21 の **Auth・Database エミュレータ**（`demo-` プロジェクト、本番に接続しない）で次を試す：<br>・他家の `priv` が読めない<br>・`pub`/`host` に書けない<br>・他席の `act` に書けない<br>・ロビー以外で席を取れない<br>・期限切れの削除だけできる |
| ③ 2端末同時の E2E（Playwright） | **別々のブラウザコンテキスト**（保存領域が別なので匿名 uid も別）を2〜4つ開き、エミュレータに接続する（ローカルだけの URL 引数で接続先を切り替え）。<br>ホストのコンテキストで部屋を作り、コードを読んで他のコンテキストで参加し、両方の画面を実際にタップして進める。<br>各端末の DOM・メモリ・受信データに他家の手牌が無いことを確かめる |
| ④ 端末内の簡易経路 | いろヨミと同じく BroadcastChannel の経路を残し、同じブラウザの2つのタブで手早く確認できるようにする（CI の主たる試験には使わない） |

### 9.1 段階1：ロビーまで

  - オフラインの通常対局・初心者の部屋・牌譜が従来どおり動く（オンラインの読込に失敗しても）

### 9.3 段階3：4・8局戦の試合通し、3〜4人、切断と復帰、再戦

  - 4・8局戦の実画面での通し、3〜4人

  - 4コンテキストで8局戦を最後まで

## 10. たたき台への意見（根拠つき）

| たたき台 | 意見 |
|---|---|
| 部屋はコード式の友達対戦のみ | 賛成。手牌の秘匿がホストを信頼する前提なので、知らない人との対戦には向かない |
| 宣言は全員の応答か制限時間で締め、時間切れはパス（15秒） | 賛成。15秒を推奨（4.2）。ただし**手番の時間制限（45秒推奨）がたたき台にない**ので追加が必要。無いと1人の離席で試合が止まる |
| 切断した席は CPU 代打ち＋復帰 | 賛成。復帰は同じ端末・同じブラウザに限られる（匿名認証のため）。ホストの切断は「猶予の間は待つ・戻れば再生で続き・戻らなければ途中終了」を提案（引き継ぎはしない） |
| ニックネームは入室時に1回、匿名認証 | 賛成。端末に保存して次回は入力を省く。不適切な名前の対策はない（友達対戦の範囲で割り切る） |
| オンライン対局は牌譜の対象外 | 賛成。将来、ゲストが「自分の視点だけ」を記録する案はあり得るが、v1 では作らない |
| 数学モードとルールセットはホストが決める | モードは賛成。**ルールセットは現行（2）に固定を推奨**。過去の版をオンラインで選べると、試験の組合せが増えるのに対し、利点が小さい |
