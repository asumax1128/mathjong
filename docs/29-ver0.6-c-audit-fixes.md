## 1. P2-1：人間がロンを見送った牌を、安全牌として危険度 0 にしてしまう

### 原因
`passedTiles()`（`src/engine/character-ai.js`）は、「宣言できるロン・ツモは必ず宣言する」という前提で、他家が今の手でロンしなかった牌を集めていた。
- 集め方：リーチ後に通った牌（本人のツモ切りを含む）と、本人の最後の打牌の後に通った牌。
- 集めた牌は、上級の危険度 v06（`dangerTableV06()`、ふくやま・アスマが使用）で確率 0 になる。
- 任意の係数 `passedSafe` でも、同じ関数を通して 0 になる（現行の係数では未使用）。

この前提が成り立つのは AI の席だけだった。
- 人間はロンもツモも見送れ、フリテンの規則もない。
- そのため、見送った牌は後でも当たりになりうる。例：リーチ中に見送った牌は、局の終わりまで当たりのまま。
- それなのに、上級 AI はその牌を「安全」と断定して捨てていた。

### 修正
- `ronGuaranteed(game, o)` を追加した。席が「ロン・ツモを必ず宣言する」と保証されるのは、`players[o].kind === 'ai'` の席だけ。
  - 人間の席、および種類が不明な席は保証しない。
  - 席が人間か AI かは画面に出ている公開情報。他家の手牌・山・本当の待ちは使わない。
- `passedTiles()` は、保証された席だけを対象にした。人間の席の「通った牌」は常に空になる。
  - これで `dangerTableV06()` と `passedSafe` の両方の経路が直る（どちらも `passedTiles()` を使う）。
  - 人間の席の危険度は、通過の履歴に関係なく回帰式の確率（常に 0 より大きい）になる。
- 前提の確認：AI 同士では通った牌を従来どおり使う。保証された AI の判断がロン・ツモを必ず宣言することをテストで確認した。
  - 9人のキャラ AI（既存）。
  - Ver.0.5-E の難易度 AI（初級・中級・上級、3つの性格。新規）。
- 新しいルール（フリテンなど）は追加していない。

### 回帰テスト（`tests/character-ai-v06-human-pass.test.js`、14件）
固定局面（山の並びを指定）は、数学Ⅰ・Ⅱのそれぞれで次の4件。

| 局面 | 内容 |

その他のテスト：

## 2. P3-1：シミュレーションの対比較（ケースの絞り込みで seed が変わる）

### 原因
`tools/sim-v06.mjs` の試合の seed は `mix(seed, ci, g, rot, length)` だった。`ci` は `--only`・`--exp` で絞り込んだ後の配列番号なので、絞り込み方が違うと同じケースでも別の対局になっていた。`tools/compare-v06.mjs` は、挑戦者の順位の配列を並び順だけで対にしていた。

### 修正
- **ケースの一意ID** `kind:level:lineup`（例 `down:-:kaoru,ousuke,natsuki,yuki`）を付けた。重複はエラー。
- **seed**：既定（`--seed-scheme case-id`）は `mix(seed, FNV-1a(ケースID), グループ, 回転, 局数)`。配列番号には依存しない。
- **出力**：試合ごとに次を記録した。JSON の `matches`、CSV にも出力する。
  - 標本ID（`ケースID|g<グループ>|r<回転>`）
  - seed（`seedBase`）
  - 席の並び
  - 最終得点・順位
  - あわせて `meta` に `seedScheme`・`only`・`human` を記録した。
- **対比較**：`compare-v06.mjs` は、両方の結果にある同じケースID の試合だけを、標本IDで対にする。
  - 次の場合はエラー：標本の集合・seed・席の並びが一致しない、`seed`・`mode`・`length`・`seedScheme`・`human` が違う、試合ごとの記録がない旧形式。
  - 片方にしかないケースは比べず、一覧を表示する。
- **互換**：`--seed-scheme index` は監査前の seed を再現するためだけに残した。`--only` と併用すると警告を出す。
  - 確認：監査前の最終評価（docs/28 の m1L4all・調整前、seed 900001）の第0グループの 84 試合を、`index` で完全に再現した。
- **検証**：
  - 単体テスト：8種類の実験 × 7通りの `--only` で、同じ標本の seed・席の並び・ケースIDが常に同じ。
  - 実対局：`--only kaoru` の有無で、同じケースの得点が同一。
  - CI：`down` 全体と `--only kaoru` を対比較し、差 0.000 を検査するステップを追加した。

### 既存の報告値への影響
- docs/28 の対比較は、すべて基準と変種で同じ `--exp`・`--only`・seed を使っていた。そのため同じ seed の対局どうしを比べており、対比較の結論は変わらない。
  - 例：ふるいは `--exp down --only fukuyama,kaoru,asuma` で、基準と変種が同一の指定。
- 最終評価（docs/28 の 5章）は `--only` を使っていない。
- ただし、`--only` で絞った実行の絶対値（例：ふるいの「ふくやま 2.299」）は、同じケースの全体実行の値と別の seed の標本だった。
- 新しい seed 方式で、修正後の数学Ⅰ・Ⅱ、4局戦・8局戦を測り直した（5章）。

## 3. P3-2：同点時の順位の集計

### 原因
1位率・2位以内率・4位率を、平均順位（同点を分け合った値）から推定していた。
- 例：`rank <= 1 → 1`、`rank < 2 → 0.5`。
- 3人同点・4人同点が誤る。4人とも100点なら平均順位は 2.5 で、1位率・4位率は 0 になっていた（正しくは 0.25）。

### 修正
`placeShares(scores)` を追加した。
- 仕組み：上に h 人、自分を含めて t 人が同点なら、h+1〜h+t 位に 1/t ずつの持分を与える。
- 率の算出：1位率＝1位の持分、2位以内率＝1位＋2位、4位率＝4位の持分を、最終得点から直接数える。
- 適用範囲：挑戦者・難易度別のまとめ（`levelAgg`）・CSV のすべて。
- 平均順位：同点の分け方は従来どおりで、Σ 順位×持分 と一致する。

単体テスト：
- 全員同点、3人同点（上位・下位）、2人同点×2、2人同点の各場合と、乱数の得点 500 通りで確認した。
  - 持分の和が1。
  - 各順位の持分を4人分足すと1。
  - 平均順位＝Σ 順位×持分。
- 集計（`playerSummary`・`summarize`）で、4人とも100点なら 1位 0.25・2位以内 0.5・4位 0.25。

既存の報告値への影響：
- 修正後のシミュレーション（6章、計 4,608 試合）の試合ごとの記録から、旧式と新式の率を同じ試合で比べた。
- 同点のある試合は 3.6〜12.6%（ほとんどが2人同点で、旧式でも正しい）。
- 旧式と新式の率の差は、試合あたりの平均で 0.001 以下、キャラ・ケースごとの最大で 0.018（数学Ⅱ 4局戦）。
- docs/28 の1位率・2位以内率・4位率への影響は、小数第2位（%表示で 1〜2 ポイント未満）にとどまる。平均順位は変わらない。

## 4. P3-3：AUC の評価

### 原因
`tools/calibrate-v06.mjs` の AUC は、予測値の順に並べた位置で順位を付けていた。そのため、同点の予測値（同じ特徴量の行は多い）の順位が入力の行の順に依存した。また、報告した AUC 0.933 は、当てはめに使った行での値（学習データ内）だった。

### 修正
- `aucOf()`：同点の予測値には平均順位を使う（正例と負例の同点を 0.5 と数える）。
  - 単体テスト：同点の多いデータを 20 回並べ替えても同じ値になる。素朴な全対の数え上げと一致する。
- 学習データ内の評価（`train`）と、当てはめに使っていない seed での独立評価（`eval`）を分けて出力する。
- Brier score、基準率だけの Brier、確率帯ごとの予測の平均と実測の割合を出力する。
- `--evaluate-current`：実行時の係数（`DANGER_COEF_V06`）を当てはめずに独立評価する。
- `--tune`：対局を作るキャラの係数を指定する。
- 実行時の係数は変更していない。
  - 確認：当てはめ当時の係数（docs/28 の BEFORE）で学習データを再生成し、同じ係数が得られた（数学Ⅰ・Ⅱとも12個すべて一致）。

## 5. E2E の待機競合（既存の P3）

### 原因
`tests/e2e/play.mjs` の `apDiscardDrawn()`（docs/HANDOFF.md の P3-1 が指す 1741 行付近と、3207 行付近の `v04bLevels` の呼び出し）は、打牌の完了を「手番が人間から他家に移った」ことで待っていた。AI が速い（`speed=test` は待ち 0 ms）と、他家3人が次の確認までに打ち終えて人間の手番に戻ることがある。その場合、条件を見逃して待ち続け、タイムアウトしうる。

### 修正
- 打牌の直前に、その牌の ID とその時点の局を覚える。
- 「その局の記録に、人間によるその牌の打牌がある」ことを待つ（継続する状態なので見逃さない）。
- 待った後、その打牌の記録がちょうど1件であること（2回タップで打牌は1回）を確かめる。
- 演出（カットイン・効果音・リーチ・ロン・ツモ）の検査はそのまま。

### 確認
- この環境で旧条件の競合を再現しようとした（`speed=test`・初級・数学Ⅰで、打牌を 186 回）。タイムアウトは 0 回で、**再現できなかった**。
- 新条件も 186 回すべて成功した。
- 修正は、監査が指摘した待ち方を、操作の完了を確実に判断できる条件に置き換えたもの。
- 関係する E2E（`chiAutoPass, chiAutoPassLayouts, v03Rules, v03bHints, v04bLevels`）は成功した。CI のブラウザ検査に `chiAutoPass` を加えた。

- 個性：9人の判断は修正の前後で、AI 同士では同一。人間の席に対する上級の判断だけが変わる。個性の指標は docs/28 の7章のまま。
- 決定論：同じ引数（ref・数学Ⅰ・seed 930001）を2回実行し、判断時間以外の出力（試合ごとの seed・席・得点・順位、集計）が完全に一致した。
- 保存則：全試合で得点の総和 400（各局の後に検査）、順位の和 10。局ごとの `checkInvariants()`（牌の保存）を満たした。
- 判断時間：上級の判断の計算は、人間の席の通過牌の集計を省くだけで、増えない。
